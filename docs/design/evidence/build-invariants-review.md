# Independent build invariant and security review

Reviewed 2026-09-13 by the mathematical/invariant review agent. Scope: native
Make dependency graph, configuration stamps, binary embedding, Python lock
generation. This is a finite implementation review, not a proof of OS security.

## Model and assumptions

Let B(S,C,T,F) produce artifacts from source S, configuration C, toolchain T,
and build flavor F. Each artifact must depend on every input it consumes.
The workspace and build scripts are trusted, source changes receive normal
filesystem timestamps, and one writer owns each flavor output directory.
Two concurrent make processes in the same output directory are unsupported.

| Invariant | Evidence / boundary |
| --- | --- |
| Idempotence: unchanged S,C,T,F preserves bytes and artifact mtimes | Real init build test passes; embedder independently preserves output mtime. This is not exhaustive for every target. |
| Invalidation: changing a consumed input invalidates every affected artifact | Effective user flags, headers and libc changes pass a real cross-compilation test. Assembly and CRT omissions below require correction. |
| Flavor isolation: distinct F use disjoint writable output paths | Standard kernel/user/musl path composition separates outputs. Special legacy recursive targets with fixed build-hyperv/build-fortress paths are outside this guarantee. |
| Archive membership equals current object set | User libc now rebuilds into a fresh temporary archive before rename; removed members cannot survive merely because ar updates existing members. One writer is required. |
| Embedded identity: generated byte arrays equal selected program bytes | Independent all-256-byte test passes; changed bytes change output. Missing files, traversal names and normalized identifier collisions reject without replacing prior output. |
| Shared resolution: each shared package has the same version across profiles when the full lock constraint applies | Generator supplies the full-profile lock as constraints to remaining solves. Different platform marker applicability can require platform-specific packages. Offline hash check proves recorded identity, not dependency satisfiability. |

## Actionable findings sent to integration owner

1. **Kernel assembly header invalidation:** the .S recipe lacks -MMD/-MP and
   DEPS includes C objects only. isr_stubs.S, user_entry.S and syscall_entry.S
   include entry_state.h. A header change can rebuild C without rebuilding
   assembly offsets. Security implication: stale syscall/interrupt layouts.
   Add assembly depfile production and inclusion; regression-test header edits.
2. **Musl CRT propagation:** hello_musl and MUSL_TEST_RULE link crt1.o, crti.o,
   crtn.o but depend only on the copied loader, their source and linker script.
   A CRT-only edit can change a linked input without changing libc.so. Include
   the CRT outputs in a checked content stamp after recursive musl build.
3. **Tool identity completeness:** kernel records CC/LD command names but no
   toolchain version. Musl records CC version and flags, but not AS, LD or
   OBJCOPY command identities. Changing those tools can leave stale artifacts.
   Version strings alone also cannot prove identical executable bytes.
4. **Packaging graph scope:** ISO prerequisites currently do not express all
   Limine and packaging-script inputs. Existing ISO success must not be treated
   as evidence that every subsequent packaging change invalidates it.

## Threat model and limits

Stale configuration or header artifacts can silently defeat an intended
hardening update; they are correctness and security failures. Distinct flavor
directories reduce accidental production/test contamination. They are not a
security boundary against a process that can write both directories.

The embedder validates names before publishing and writes atomically. It does
not authenticate binary producers or defend against concurrent replacement of
input files between stamp hashing and embedding. Build under a single trusted
writer. A malicious programs.mk can already execute Make syntax: its contents
are trusted source, not a sandboxed manifest. The Python catalog similarly
contains trusted output paths; it must not accept external untrusted catalogs.

Python --check verifies generated profile text, input fingerprints and lock
fingerprints. It fails on drift relative to the recorded snapshot; an attacker
who can rewrite both locks and snapshot can replace the trust anchor. The
check alone does not install packages, validate wheel compatibility, or prove
absence of vulnerable dependencies. Lock generation writes outputs sequentially;
an interrupted solve can leave mixed files, detectable by the final snapshot
check. Release automation should require that check before installation.
