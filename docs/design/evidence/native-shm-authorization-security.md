# SHM destruction authorization: independent design review

Reviewer: `/root/mcp_upgrade`. Initial source: `fedd602`. Date: 2026-09-15. Read-only source review; no runtime or completed-fix claim.

The current public destruction boundary is reachable from `kernel/src/ipc/ipc.c:sys_shm_destroy` without caller authentication. The creator-release flag in `shm.c` prevents repeated reference consumption but does not establish ownership. Authorization must occur under the registry lock before changing that flag or the reference count. Foreign attempts must preserve both creator ownership and existing mappings.

## Recommended bounded contract

1. Give each task an immutable, nonzero creation identity allocated without wrap/reuse, and store that identity with the SHM creator. Do not authorize by PID/TID alone: `task.c` has its own allocator, `exec.c` forks from a separate counter starting at 100, and `exec_syscall.c` clones from 300. Prior idle/init PID collisions are established evidence. Explicitly select task-local creator policy or a separately owned thread-group identity; neither CLONE_VM nor copied task memory should implicitly confer destruction authority.
2. Make public destruction require a matching current identity. Keep mapping/temporary-reference release private and independently owned. If kernel housekeeping needs delegated destruction, use an explicit trusted API rather than a NULL-current or PID-zero/one privilege fallback. A raw task pointer is insufficient because allocator reuse can create an ABA identity match.
3. Replace reused slot-index handles with slot-plus-generation handles, or another nonreused opaque identifier. Exact handle validation must occur inside locked lookup; slot reuse must advance generation, and exhaustion must fail closed rather than wrap. Apply lookup to every SHM operation, including find, size, map, unmap and internal mapping records. A stale same-creator handle is otherwise enough to destroy a replacement region.
4. Reject syscall IDs with nonzero upper 32 bits before conversion to `vos3_ipc_id_t`. Current casting aliases attacker-supplied 64-bit values to valid handles. Also reject invalid/reserved encodings rather than masking them into valid slots.
5. Replace direct Linux ABI aliases with argument-aware wrappers. Syscall 31 currently calls destroy while ignoring the shmctl command: unsupported IPC_STAT/IPC_SET/unknown commands must not destroy anything. Supporting only IPC_RMID initially is a clear bounded contract. Existing shmget/shmat/shmdt aliases also have different argument layouts; either translate them correctly or reject unsupported operations explicitly.

## Required evidence and remaining boundaries

Native negative tests must exercise a foreign process against a live victim region, then prove owner mapping contents, backing references and creator destruction still work. Include CLONE_VM identity policy, stale handle after actual same-slot reuse, same numeric TID with different creation identity, high-bit syscall truncation, unsupported Linux control commands and duplicate creator close. Preserve creator-first explicit-detach and final-AS-reap cleanup controls. Classifier acceptance must require negative outcomes plus victim liveness, not merely absence of a panic.

Concurrent raw lookup/unmap lifetime, arbitrary IPC capability delegation, creator death reclamation, credential changes and global process-ID uniqueness remain separate contracts. This review proposes a bounded correction to destruction authorization and stale handles; it does not certify full SysV IPC compatibility or all IPC security. Production implementation and artifact-bound native validation are pending.

## Coordinator contract and dispatcher reachability review

The coordinator selected task-local immutable 64-bit creation cookies assigned under the task registry lock, with exhaustion refusal; 32-bit generation/slot SHM handles capped at INT32_MAX for existing signed clients; exact checked public destruction; and separate explicit trusted housekeeping if required. This is consistent with the bounded recommendation. Clone/fork registration must assign a fresh cookie after memcpy; exec policy must explicitly state whether the same task retains creator authority.

The dispatcher cleanup paths are not both inherently trusted. `dispatcher.c:sys_agent_deregister` is user-reachable and validates only the numeric TID against its agent slot. Replacing its destruction call with a trusted bypass would create a future confused-deputy route when slot/SHM association is populated. Keep this call on the checked creator-identity API. `sys_agent_kill_all` explicitly checks TASK_FLAG_KERNEL, while a separate virtio bridge command also invokes global cleanup; bridge/operator authorization remains a distinct review boundary. A bounded source search found only negative initialization of `prefetch_shm_id`, not positive assignments, so the cleanup branches are currently dormant in the inspected implementation. Dormancy is not a justification for an unguarded future privilege path.

Only global kernel-owned cleanup should receive an explicit trusted-release API. Do not silently extend that bypass to syscall-reachable deregistration. Tests and settled production diff are still pending.

Final coordinator choice: no trusted public API is introduced. Both dormant dispatcher cleanup sites retain checked destruction; cross-owner housekeeping fails closed until an explicit authority protocol is implemented. Private mapping/temporary puts retain their owned-reference semantics and do not consume creator authority. This avoids expanding the privilege surface during the current fix.

## Settled production diff: pre-runtime assessment

Independently reviewed task/header, SHM registry and syscall wrapper changes. Task creation and registration assign a fresh nonzero 64-bit cookie while holding the task registry lock; fork/clone registration replaces the memcpy-inherited value before publication. The field is appended, preserving existing field offsets. Public destruction compares the caller cookie with the stored creator cookie under the same registry lock that protects creator-close/refcount mutation. No trusted bypass was added. Exec keeps the same task identity, so creator authority follows that task through exec; this is task identity, not executable identity or a user-account credential.

Handles reserve six slot bits and use a monotonically advancing generation capped below the signed 32-bit boundary. Lookup rejects invalid encoding and compares the complete stored handle; slot exhaustion retires the slot rather than wrapping. All changed table writes and creator-close flag accesses derive the slot explicitly; find returns the full generation-tagged handle. Size lookup now holds the registry lock. Public SHM ID wrappers reject high bits before narrowing, and syscall 31 rejects unsupported commands before destruction. Normal creation rejects the device flag and rounding overflow. No sequential creator-authorization blocker was found in these inspected paths.

The native user control separately tests private/public foreign fork denial on both destruction entry points, private mapping denial, public mapping preservation after creator close, exact same-slot replacement with a distinct handle, stale-handle denial, unsupported commands and high-bit aliases. It checks full victim-page content and process progress, with no inherited mapped SHM at fork. Requested additional map/unmap/size high-bit controls, stale unmap and shared-VM creator-denial coverage from the test author. Identity collision/exhaustion and generation exhaustion need focused supporting controls before claiming those edge paths were executed.

Independent freestanding Clang syntax checks passed for all three changed C implementation files and the integrated user test, with existing GCC-specific warning-pragma warnings. Eight observer tests passed. No new native run has been reviewed yet. Remaining scope limits include kernel-AS mapping shortcuts, raw concurrent unmap lookup lifetime, zero-creator bootstrap housekeeping, creator death reclamation, and the still-incomplete Linux shmget/shmat/shmdt argument translations. These do not constitute approval of full IPC semantics or all mapping authorization.
