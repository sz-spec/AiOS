# VOS3 EU AI Act — Audit Export Bundle Schema (`vos3.eu_act.v1`)

**Status:** v21.4.0-EU-ACT-ALPHA
**Driver document:** `docs/plans/PHASE_6_1_KILLER_FEATURE.md`
**Regulatory anchor:** EU AI Act (Regulation (EU) 2024/1689) Articles 12, 19, 26
**Enforcement deadline:** 2026-08-02 — high-risk AI logging obligations
**Days remaining at write time:** 92

---

## §0. Purpose

This document specifies the on-wire format for VOS3's regulator-facing
audit export. The format is derived from the kernel's MMR (Merkle
Mountain Range) audit chain (`kernel/src/sec/mmr_audit.c`) — every
syscall recorded by the kernel becomes one MMR leaf. The export
re-packages a time-bounded slice of the leaf log into a single signed
bundle that an enterprise CISO can hand to a Member State auditor.

The schema is **forward-only**: `vos3.eu_act.v1` is the wire identifier
for this revision. Future revisions will increment the suffix
(`v2`, `v3`, …); a verifier MUST refuse a bundle whose `manifest.schema`
does not match a version it knows.

---

## §1. EU AI Act mapping

### §1.1 Article 12 — Logging obligations

> *Member States and the Commission may require providers of high-risk
> AI systems to make available the logs that have been automatically
> generated by their high-risk AI systems […] for the purposes of
> preserving evidence of conformity […] and to facilitate post-market
> monitoring.* — Regulation (EU) 2024/1689 Art. 12

VOS3 satisfies this obligation by producing **every** syscall as a
tamper-evident MMR leaf. The leaf carries enough state for an auditor
to reconstruct the AI system's behavior across a defined time window.

### §1.2 Article 19 — Automatic logging retention

> *Providers of high-risk AI systems shall ensure that logs generated
> by the high-risk AI systems […] are kept for a period appropriate
> in light of the intended purpose of the high-risk AI system.* — Art. 19

The bundle is the operator's evidence of compliance: a single signed
artifact that survives system re-deployment, hardware replacement, and
operator turnover. The MMR root carried in the manifest cryptographically
pins the bundle's contents to the kernel state at export time.

### §1.3 Article 26 — Provider obligations on serious incidents

> *Providers shall report […] any serious incident […] to the market
> surveillance authorities.* — Art. 26

The verify tool (`tools/vos3_eu_act_verify.py`) lets an auditor
independently confirm that the bundle has not been altered between
export and submission. This satisfies the chain-of-custody requirement
implicit in Art. 26 — the operator cannot tamper with the evidence
they themselves submit.

## §2. Bundle layout

```
vos3_audit_bundle.zip
├── manifest.json           — JSON, exactly one
├── leaves.ndjson           — newline-delimited JSON, one MMR leaf per line
├── proofs/
│   ├── 0.json              — Merkle inclusion proof for leaf index 0
│   ├── 1.json
│   ├── …
│   └── N-1.json            — proof for last leaf in the export window
└── signature.bin           — Ed25519 detached signature, 64 bytes
```

**ZIP constraints:**
- Stored or DEFLATE compression. No encryption (the bundle is signed,
  not sealed; the regulator must be able to inspect contents).
- Path separators: forward slash, no leading slash.
- File names: ASCII; UTF-8 byte names rejected.
- Maximum bundle size: **256 MiB** (verifier MUST refuse larger; the
  tool batches multi-day exports into multiple bundles).

## §3. `manifest.json`

```json
{
  "schema": "vos3.eu_act.v1",
  "generated_at_utc": "2026-05-02T12:34:56Z",
  "generator": {
    "tool": "vos3_eu_act_export",
    "version": "v21.4.0-EU-ACT-ALPHA",
    "host_kernel_sha256": "<hex 64 chars>",
    "host_build_flavor": "PRO" | "CORE"
  },
  "host": {
    "fingerprint_sha256": "<hex 64 chars — from license_check.c>",
    "region_code": "EU" | "US" | "IL" | …,
    "is_eu_region": true | false
  },
  "range": {
    "since_utc": "2026-05-01T00:00:00Z",
    "until_utc": "2026-05-02T00:00:00Z",
    "leaf_count": 12345,
    "first_leaf_index": 0,
    "last_leaf_index": 12344
  },
  "mmr_root_at_export": "<hex 64 chars>",
  "signature": {
    "alg": "Ed25519",
    "public_key": "<hex 64 chars>",
    "issuer": "self" | "vos3-ca",
    "key_provenance": "host_fingerprint" | "vos3_pro_lic"
  }
}
```

### §3.1 Field semantics

| Field | Required | Validation |
|---|---|---|
| `schema` | yes | MUST be exactly `vos3.eu_act.v1` |
| `generated_at_utc` | yes | RFC 3339, UTC, second precision |
| `generator.host_kernel_sha256` | yes | SHA-256 of the running `vos3.elf` |
| `generator.host_build_flavor` | yes | One of: `PRO`, `CORE` |
| `host.fingerprint_sha256` | yes | Hardware fingerprint per `kernel/src/pro/license_check.c` (CPUID + TPM EK + MAC) |
| `host.region_code` | yes | ISO-3166-1 alpha-2 OR `EU` for non-specific EU |
| `host.is_eu_region` | yes | true iff Article 12 enforcement applies to this host |
| `range.since_utc`, `range.until_utc` | yes | RFC 3339, UTC, since ≤ until |
| `range.leaf_count` | yes | Equals `last_leaf_index - first_leaf_index + 1` |
| `mmr_root_at_export` | yes | SHA-256 of the MMR root at export-tip — pinned via TPM PCR if available |
| `signature.alg` | yes | MUST be `Ed25519` |
| `signature.public_key` | yes | 32-byte Ed25519 public key, hex |
| `signature.issuer` | yes | `self` (host fingerprint key) OR `vos3-ca` (PRO certified) |

## §4. `leaves.ndjson`

One JSON object per line, no embedded newlines. Each object:

```json
{
  "index": 12345,
  "timestamp_tsc": 1234567890123456,
  "timestamp_utc": "2026-05-02T12:34:56.789Z",
  "syscall_nr": 257,
  "tid": 42,
  "uid": 1000,
  "args_hash": "<hex 16 chars — truncated SHA-256 of arg buffer>",
  "result_class": "ok" | "err" | "killed",
  "result_value": -22,
  "leaf_hash": "<hex 64 chars — SHA-256 of the canonicalized leaf body>"
}
```

### §4.1 Determinism

The `leaf_hash` is the **canonical** SHA-256 of a stable byte
serialization of the leaf body — independent of the JSON
representation. Two verifiers reading the same NDJSON line MUST
arrive at the same `leaf_hash` value. The kernel computes this hash
inside `mmr_append()` before the leaf is appended to the chain;
the export tool re-computes it from the NDJSON to detect any
mid-flight tampering with the bundle.

### §4.2 Privacy

`args_hash` is a **truncated** hash, not the raw syscall arguments.
This satisfies GDPR data-minimization (Article 5(1)(c)) — the
auditor can verify *which syscall* fired and that the *arguments
were stable* without reconstructing the arguments themselves. If a
specific incident requires arg reconstruction, the operator can
re-export with `--include-args` (subject to a separate consent
gate documented in `regional_policy.py`).

## §5. `proofs/<leaf_index>.json`

Merkle inclusion proof from `leaf_hash` up to `mmr_root_at_export`:

```json
{
  "leaf_index": 12345,
  "leaf_hash": "<hex 64 chars>",
  "siblings": [
    {"h": "<hex 64 chars>", "side": "R"},
    {"h": "<hex 64 chars>", "side": "L"},
    …
  ],
  "mmr_root": "<hex 64 chars — must match manifest.mmr_root_at_export>"
}
```

The `siblings` list is ordered from the leaf's immediate sibling
upward to the root. Each entry has a `side` field:

- `side: "R"` — sibling is to the RIGHT of the current node;
  parent = `sha256(current || sibling)`
- `side: "L"` — sibling is to the LEFT of the current node;
  parent = `sha256(sibling || current)`

Verification:

```python
h = bytes.fromhex(leaf_hash)
for sib in siblings:
    sib_bytes = bytes.fromhex(sib["h"])
    if sib["side"] == "R":
        h = sha256(h + sib_bytes).digest()
    else:  # "L"
        h = sha256(sib_bytes + h).digest()
assert h.hex() == mmr_root
```

**Backwards-compat note:** The v21.4.0 ALPHA used a flat string list
(implicit `side: "R"`) which only verified correctly for left-child
leaves. v21.4.3+ uses the direction-tagged form above. Verifiers
SHOULD accept a plain hex string as equivalent to `{"h": ..., "side": "R"}`
for cross-revision compatibility, but exporters MUST emit the tagged form.

The MMR's height-doubling structure means most leaves have
`O(log n)` siblings — for a million-leaf chain, ~20 siblings per
proof, ~640 bytes per proof file.

## §6. `signature.bin`

64-byte Ed25519 detached signature over the canonical
representation of:

```
sha256(manifest.json) || sha256(leaves.ndjson) || sha256(SORTED_PROOFS_TARBALL)
```

Where `SORTED_PROOFS_TARBALL` is a deterministic tar of the
`proofs/` directory with files in lexicographic name order
(`0.json`, `1.json`, `10.json`, `100.json`, …, `2.json`, …).
The tar uses POSIX format, no extended attributes, and zero
mtime/uid/gid — this makes the signed digest independent of
local filesystem state.

### §6.1 Key provenance

| Issuer | Key source | Verifier action |
|---|---|---|
| `self` | Ed25519 keypair derived from host fingerprint | Verifier accepts; trust scope is "this host attests" |
| `vos3-ca` | Cross-signed by VOS3 PRO CA (issued via `tools/vos3_pro_activate.py`) | Verifier validates CA chain; trust scope is "VOS3 attests this is a licensed PRO host" |

The `self`-signed bundle is sufficient for Art. 12 compliance
because the auditor can independently re-derive the host
fingerprint and confirm the public key matches the host they
sampled.

## §7. Verifier contract (`tools/vos3_eu_act_verify.py`)

A bundle is **valid** iff ALL of the following hold:

1. ZIP opens cleanly; entry list matches §2 layout (extra files = invalid).
2. `manifest.json` parses; `schema == "vos3.eu_act.v1"`; required fields present.
3. `leaves.ndjson` line count == `manifest.range.leaf_count`.
4. Every line's `leaf_hash` re-computes to the same value when canonicalized.
5. `proofs/` contains exactly `leaf_count` files; names are `0.json` through `(leaf_count-1).json`.
6. Every proof verifies up to `manifest.mmr_root_at_export`.
7. `signature.bin` is exactly 64 bytes.
8. Ed25519 verification of the §6 digest succeeds against `manifest.signature.public_key`.
9. If `manifest.signature.issuer == "vos3-ca"`, the public key is signed by the embedded VOS3 CA cert.

A bundle that fails ANY check above is **invalid**. The verifier
prints which check failed and exits with a non-zero status.

## §8. Operator workflow (typical)

```bash
# Operator (export side):
vos3_eu_act_export.py \
    --since 2026-05-01T00:00:00Z \
    --until 2026-05-02T00:00:00Z \
    --output  audit-2026-05-01.zip \
    --signing-key  $VOS3_HOST_KEY

# Auditor (verify side):
vos3_eu_act_verify.py audit-2026-05-01.zip
# →
# vos3.eu_act.v1 bundle valid
# host kernel SHA: 6c96ab37…
# host fingerprint: a85f2f32…
# leaf range: 0..12344 (12345 leaves)
# MMR root: ce5129d6… (reproduced from proofs)
# signature: Ed25519 (issuer=self, fingerprint-key)
# RESULT: PASS
```

## §9. What's NOT in `vos3.eu_act.v1`

These are deferred to future schema revisions; including them now
without regulator-side validation tools would be premature
standardization:

| Item | Target rev | Reason |
|---|---|---|
| GDPR Article 30 record-of-processing field | v2 | Different regulator surface |
| Trust Registry interop (EBSI) | v2/v3 | Standard still in flux 2026-Q2 |
| Multi-host bundle aggregation | v3 | Federation pattern unclear pre-Aug-2 deadline |
| WASM-in-slot `secure_compute` attestation | v3 | Phase 7 / v20.6 dependency, not landed |
| Full-args inclusion w/ consent token | v2 | Needs operator-side consent UI |

This rev focuses on the **minimum compliant export** that an
operator can produce on Aug 2 2026 and an auditor can independently
verify with the public-domain tooling shipped in this repo.
