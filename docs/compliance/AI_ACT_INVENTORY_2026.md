# VOS3 — EU AI Act Component Inventory & Risk Classification
## Article 12 Compliance Evidence Package
**v20.3.0 | April 2026 | FOR: Legal, Compliance, Notified Bodies, EU Auditors**

---

## 1. Document Purpose

This inventory catalogs every AI-bearing component of the VOS3 platform,
classifies it under the EU AI Act risk tiers, and documents the evidence
that supports each classification. It is the operator's primary compliance
artifact for the August 2, 2026 enforcement deadline.

This document is **not** legal advice. It is a technical declaration
prepared by the engineering team to support legal review.

---

## 2. Risk Classification Methodology

The EU AI Act establishes four risk tiers (Articles 5–52):

| Tier | Definition | VOS3 components |
|------|-----------|----------------|
| **Unacceptable Risk** (Art. 5) | Banned: social scoring, exploitative manipulation, real-time biometric ID in public spaces (with narrow exceptions) | None |
| **High Risk** (Annex III) | Education, employment, essential services, law enforcement, migration, justice, biometric ID, critical infrastructure | None — see §6 boundary statement |
| **Limited Risk** (Art. 52) | Transparency obligations: chatbots, emotion recognition, deepfake / synthetic content | Chat, Code Builder, Multi-Agent System, Proactive Intelligence, Voice Input |
| **Minimal Risk** | Spam filters, AI in video games, inventory management — no specific obligations | V-Core Business OS, Convex/Stripe/Clerk integrations, Kernel + MMR infrastructure |

VOS3 operates **exclusively at the Limited Risk and Minimal Risk levels**.
No component performs biometric identification, automated decisions in
employment / credit / education, or real-time public-space surveillance.

## 3. Component Inventory

### 3.1 VOS3 Chat (`/api/chat/*`)

| Field | Value |
|-------|-------|
| **Risk Tier** | Limited Risk |
| **Article** | Art. 52(1) — chatbot transparency obligation |
| **Intended Purpose** | General conversational AI assistant for software-engineering and business productivity tasks. Generates code, documents, explanations, and proposals on user request. |
| **Deployer (Operator)** | The VOS3 license holder (typically the customer) |
| **Provider** | VOS3 Project (this repository) |
| **Models used** | GPT-4o, Claude Sonnet 4.6 (default); Claude Haiku 4.5 (degraded mode); local Gemma-4-27B / Llama-3.3-70B (privacy mandate) |
| **Transparency disclosure** | UI labels every assistant message with "V" persona indicator. The chat composer carries an "AI Chat" header. The `ChatResponse` schema returns `model` and `provider` fields surfaced in the UI. |
| **Data retention** | Conversation summaries persisted to user's Convex namespace under user-controlled retention. Raw turns NOT retained beyond the session unless user explicitly saves a project. |
| **Logging** | MMR audit chain (kernel-side) records every syscall; backend logs include `model_id` per request without PII. |

### 3.2 Code Builder (`/api/codegen/*`)

| Field | Value |
|-------|-------|
| **Risk Tier** | Limited Risk |
| **Article** | Art. 52(3) — synthetic content disclosure (the system generates source code that may be distributed as if human-authored) |
| **Intended Purpose** | Generate source code from natural-language descriptions. Output is provided to a developer for review, modification, and integration. |
| **Provider safeguards** | Generated files include a `// Generated by VOS3` header where the language convention permits. The Live Preview environment runs all generated code in a Sandpack sandbox isolated from the user's filesystem. |
| **Models** | Claude Sonnet 4.6 (default); local Qwen2.5-Coder 72B (privacy mandate) |
| **Out of scope** | Code generated by VOS3 is not deployed automatically to production — the user is the deployer. The user is responsible for review prior to deployment. |

| Field | Value |
|-------|-------|
| **Risk Tier** | Limited Risk |

## 4. Article 12 Compliance Evidence — Detailed Mapping

EU AI Act Article 12 imposes four obligations on AI systems with logging
requirements. The table below maps each obligation to its VOS3 implementation.

| Article 12 Obligation | VOS3 Implementation | Code Reference |
|-----------------------|--------------------|----------------|
| **(1) Automatic logging** — events recorded without operator intervention | `mmr_record_syscall()` is called from `syscall_dispatch()` on every syscall — no manual trigger | `kernel/src/sec/mmr_audit.c` |
| **(2) Tamper-evident records** | SHA-256 Merkle Mountain Range chain. Modifying any historical record requires finding a SHA-256 collision (2¹²⁸ operations bound). | `kernel/src/sec/mmr_audit.c` (height-byte domain separation, RDSEED entropy binding) |
| **(3) Retention period** | Root hashes pinned to Convex transparency log; backend can retain pinning records for 6+ months per operator configuration | `backend/api/kernel_routes.py:355` (`/transparency`) |
| **(4) Verifiable by third party** | O(log N) inclusion proof via `GET /api/kernel/transparency`. Auditors can verify any leaf without downloading the full chain. Pure-Python reference verifier shipped: `tools/vos3_verify.py`. | `tools/vos3_verify.py` |

The MMR audit chain is **mathematically irreversible** — see the formal
proof in `docs/final_launch/VOS3_INVESTOR_MEMO.md` §3 (Theorem 3 — MMR
Tamper Detection Bound).

## 5. EU/EEA Regional Enforcement

For users detected as being inside the EU/EEA region, VOS3 enforces a
mandatory local-first inference path that prevents data egress. See
`docs/final_launch/EU_COMPLIANCE_STRATEGY.md` for the complete spec.

| Component | Behavior for EU users |
|-----------|----------------------|
| Region detection | `cf-ipcountry` / `x-vercel-ip-country` / `x-appengine-country` / `x-region` headers checked in fixed priority. 27 EU member states + 3 EEA states (NO/IS/LI). |
| Routing path | `regional_policy.assign_eu_local_or_sovereign()` runs as the highest-priority gate. Cloud is structurally unreachable for an EU user without explicit `global_cloud_processing_consent` in user metadata. |
| Failure mode | If local Ollama AND sovereign cloud are both unavailable, the request is **denied with HTTP 403** (`EUComplianceError`) — never silently falls back to a non-EU cloud provider. |
| Audit trail | Every enforcement decision logged with the canonical hash `SHA-256("OP_LOCAL_ENFORCEMENT_EU")` = `ca095456b27e291ff80d778a5aa6fc167ec9d59134b7e0e580d5045c6c131524` (deterministic, externally verifiable). |

## 6. Boundary Statements (What VOS3 Is NOT)

To avoid ambiguity in classification:

- VOS3 is **not** a high-risk system under Annex III. Specifically, VOS3 does not:
  - Perform biometric identification or categorization
  - Score creditworthiness or insurance risk
  - Decide or influence employment / promotion / dismissal
  - Evaluate students or test takers
  - Make decisions about access to essential public services
  - Operate as critical infrastructure (transport, water, gas, electricity)
  - Operate within law enforcement, migration, asylum, or border control
  - Operate within the administration of justice
- VOS3 is **not** a general-purpose AI model under Title VIIIA. The foundation
  models VOS3 deploys (Claude, GPT, Gemini, local Llama / Gemma / Qwen) are
  GPAI; their providers carry Title VIIIA obligations. VOS3 is a downstream
  provider deploying these models for Limited Risk applications.
- VOS3 is **not** a deepfake generator under Art. 52(3) for image / audio /
  video synthesis. It generates text and code only. The Vision pipeline
  (`backend/ai/agents/vision_agent.py`) consumes images for layout analysis;
  it does not generate synthetic faces, voices, or videos.

## 7. Operator Responsibilities (Outside VOS3 Scope)

VOS3 is the **provider** of the platform. The operator (license holder /
deployer) is responsible for:

1. **Use case classification** — the operator must classify their specific
   deployment under the AI Act tiers. If the operator uses VOS3 to build
   a high-risk application (e.g., automated CV screening), the operator's
   application becomes High Risk even though VOS3 itself is Limited Risk.
2. **End-user notification** — operators must inform their end users that
   they are interacting with an AI system per Art. 52(1). The VOS3 UI
   provides "V" persona labels and per-message provider attribution to
   support this disclosure.
3. **Data residency** — operators serving EU users must ensure
   `VOS3_EU_SOVEREIGN_CLOUD_URL` is configured OR local Ollama is reachable.
   Without one of these, EU users will see HTTP 403 for non-local routing.
4. **Logging retention** — operators are responsible for configuring the
   Convex transparency log retention to meet their applicable retention
   period (6+ months for Article 12 high-risk; shorter for Limited Risk).
