## `kernel/src/init/embedded_bins.c` — analysis

### What the file is

A 684,144-line C file. The header comment is unambiguous:

```c
/* Auto-generated embedded binaries */
#include <stdint.h>
#include <stddef.h>

/* Embedded: init */
const uint8_t _embedded_init[] = {
  0x7f, 0x45, 0x4c, 0x46, 0x02, 0x01, 0x01, 0x00, ...
```

Each user-space binary in `user/build/` is converted to a `const uint8_t[]` array via `xxd -i` and concatenated into this single source. The kernel image then includes the entire suite of user-space tools as bundled resources, no separate filesystem load required.

The generator script lives at `kernel/tools/embed_binaries.sh` and runs as part of `make`. The output is therefore deterministic for a given set of input binaries — but it is **not deterministic across toolchain rebuilds**, because each user-space binary's ELF metadata depends on whatever toolchain produced it.

### What's in the diff (byte-level)

Both HEAD and working tree contain the same **79 named binaries** with the same `_embedded_<name>` symbols. Nothing was added, nothing was removed. The only difference is per-binary byte content and the corresponding `_embedded_*_size` constants.

Per-binary delta histogram (working-tree size − HEAD size):

| Δ bytes | Count | What it likely means |
|---:|---:|---|
| −24 | 51 | ELF metadata strip (e.g., `.note.gnu.property` removed) |
| −32 | 25 | ELF metadata strip + 8-byte alignment artifact |
| −16 | 1 | `auxv_interp` — partial strip |
| −8 | 1 | `hello_musl` — partial strip |
| **−47,096** | **1** | **`init` — outlier, see below** |

**All 79 binaries shrunk.** None grew. The narrow band of −24 / −32 across 96% of the catalog is the unmistakable fingerprint of a uniform ELF post-processing change (most likely `strip --strip-unneeded` or a build flag toggling out a small note section), not a behavioral change in any of the user-space programs.

### The init outlier

```
_embedded_init_size       136736 → 89640    (Δ −47,096 bytes,  −34.4%)
```

`init.c` source is **byte-identical** to HEAD, so this is not a code change. Possible causes:

1. **Debug section stripped**. `init` may have previously been built with `-g` and shipped with `.debug_info` etc.; now those sections were dropped. 47 KB is in the right order of magnitude for a small program's full DWARF tables.
2. **Different optimization level**. Going from `-O0` → `-Os` on a non-trivial init program can shed tens of KB.
3. **Compiler/linker upgrade**. Less likely — the other 78 binaries shrunk uniformly by 24/32 bytes, suggesting they were not re-optimized at a level that would have changed `init` by 47 KB.

The most parsimonious explanation: **init was built with debug sections in HEAD, and rebuilt without them in the working tree.** This is common when toggling between developer / release modes in the build system.

### Security / boot / tool-inventory impact

| Question | Answer |
|---|---|
| Are any user-space tools added or removed? | **No.** Same 79 binaries, same names. |
| Is the kernel attack surface different? | **No.** Same code paths, same syscalls, same musl ABI surface. |
| Is boot speed affected? | **Negligibly.** ~50 KB total saved across the whole embedded suite — well below noise threshold for a kernel that ships multi-MB embedded resources. |
| Is the code stable? | **Yes.** Auto-generator is deterministic; this is not half-written work. |
| Can it be regenerated reproducibly? | **Yes.** A clean `make user && make kernel` should produce the same dirty state byte-for-byte (assuming the same host toolchain). |

**Verdict**: zero functional change. Pure toolchain artifact.

## `user/musl/lib/libc.so.debug` — analysis

### What the file is

```
$ file user/musl/lib/libc.so.debug
ELF 64-bit LSB shared object, x86-64, version 1 (SYSV), static-pie linked,
with debug_info, not stripped
```

The unstripped debug companion to musl's `libc.so`. Contains DWARF debug info, symbol tables, and section headers that are absent from the production `libc.so`. Used by:

- `gdb` / `lldb` when debugging musl-linked user programs that crash inside libc
- The kernel's symbol resolver if it needs to attribute a fault to a libc function
- Coverage and profiling tools

### What changed

```
$ git diff --stat HEAD -- user/musl/lib/libc.so.debug
user/musl/lib/libc.so.debug | Bin 3018480 -> 3018472 bytes
```

**−8 bytes.** Eight. That is well within the noise floor for any ELF rebuild — likely a single section-header alignment or build-id padding change. There is no semantic content here.

### Why the rebuild happened

Filesystem evidence is decisive. Every artifact in `user/musl/lib/` shares the same mtime:

```
$ ls -la user/musl/lib/
-rw-r--r--   1 sz  staff     4608  4 May 17:49 crt1.o
-rw-r--r--   1 sz  staff      872  4 May 17:49 crti.o
-rw-r--r--   1 sz  staff      640  4 May 17:49 crtn.o
-rwxr-xr-x   1 sz  staff   638056  4 May 17:49 libc.so
-rwxr-xr-x   1 sz  staff  3018472  4 May 17:49 libc.so.debug
-rw-r--r--   1 sz  staff     4608  4 May 17:49 Scrt1.o
```

A single rebuild pass at **4 May 17:49** produced all six artifacts. Five of them happen to match the bytes already in HEAD (they're either tracked-but-unchanged or gitignored). Only `libc.so.debug` shifted by 8 bytes.

This is the **same rebuild pass** that triggered the embedded-binary regeneration. Both files are downstream of `make user`.

### Should it be deleted?

**No.** It's a working dev artifact, not garbage. Deleting it locally would:

- Break gdb sessions that try to load musl symbols.
- Force an immediate full rebuild on the next `make` (because `libc.so.debug` is a build target).
- Lose nothing useful, since it'll come right back on the next build.

The only relevant question is whether to **commit** the 8-byte delta. The same logic as `embedded_bins.c` applies: it's noise.

## Toolchain hypothesis (one-line summary)

Someone ran `make` (likely `make user-clean && make user && make kernel`) on **4 May at 17:49** with a host toolchain that produces ELFs ~24–32 bytes smaller per output than the toolchain that produced HEAD's binaries — and either changed the init build flags to drop debug sections, or this rebuild is the first one after a `-g` → no-`-g` flip in the init Makefile.

The result is fully deterministic for the new toolchain configuration. No work is lost; no work is gained. The git diff exists only because git tracks bytes, not semantics.

## Recommendation: **Discard, don't commit**

### Reasoning

1. **No source change.** Verified: `init.c`, `init_binaries.c`, and every `.c` under `user/musl/` are byte-identical to HEAD. The drift is exclusively in build output.
2. **Cost-to-benefit is wrong.** A commit would add ~50 MB to git history for zero behavioral content. Future clones pay forever; future developers reading the log get no information.
3. **Reversibility is free.** The exact same dirty state will reappear on the next `make user` for any developer with the same host toolchain. There's no work to lose.
4. **The 8-byte `libc.so.debug` delta is meaningless.** It's debug metadata padding.
5. **Pre-existing precedent isn't a fit.** Commit `a03aa52` ("chore: regenerate embedded_bins.c with musl ldso + hello_musl") *added a new binary* (`hello_musl`) — the regen was downstream of an actual scope change. The current drift has no source-side delta to justify it.

### When you might commit anyway

- **Reproducible-build CI gate.** If your CI checks that `embedded_bins.c` in the repo matches `embedded_bins.c` produced by a fresh build, then committing the regenerated version is the only way to keep CI green. This is a real argument *if* such a gate exists.
- **Branch is going stale and a teammate needs the same toolchain output.** A regen commit on a feature branch means downstream pulls don't have to rebuild before testing. Marginal benefit.
- **You're about to retire this branch.** A final cleanup commit is fine; just title it accurately ("chore: post-Gold-Master regen of embedded_bins.c, no source change").

If neither of those applies, discard.
