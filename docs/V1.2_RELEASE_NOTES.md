## TL;DR — the breakthrough

**vOS v1.2 moves AI-agent information-flow control from the interpreter into the kernel.**

Every prior agent-security product — including vOS v1.1 — enforces "don't let the agent leak this data" in *userspace*: a Python guard, an LLM-side filter, a policy engine the agent's own process could in principle bypass. v1.2 closes that gap. A compromised agent process that side-steps every Python-level check now hits **`-EPERM` at the `write()` / `sendmsg()` syscall**, enforced by an eBPF LSM program that reads per-byte taint labels the agent runtime cannot forge.

Three composable guarantees — the **Triple-Threat** — ship together:

| | Guarantee | Layer | "What it stops" |
|---|---|---|---|
| **[B]** | Identity Federation (SPIFFE / AIMS) | cross-org | An agent from another org acting without verifiable, hardware-attested identity |
| **[C]** | Byte-Level IFC (eBPF Kernel Gate) | kernel syscall | Prompt-injection exfiltration that bypasses the userspace guard |
| **[C-3]** | Cryptographic Declassification (Ed25519) | audit | Silent / forgeable "this data was cleared for egress" claims |

These compose: a **federated** agent (B) whose tool output is **byte-colored** (C) may egress **only reviewed bytes** (C-3) — and the gate is in the kernel, not the interpreter.

## [C] Byte-Level Information Flow Control — the kernel gate

**Catalog item:** C7 (was "partial / userspace-only" at Sprint 16 → "full-stack" at v1.2).

### The problem (from the agent-era OS catalog)

> *"No OS-level taint-tracking for data tainted by untrusted input. Information flow control (IFC) at OS level was researched in the 1990s (HiStar, Asbestos) but never mainlined; the agent era resurrects the need."*

EchoLeak (the first confirmed zero-click prompt-injection data-exfil in a production AI system, Microsoft 365 Copilot, disclosed June 2025) is the canonical motivating attack: a web page contains a clean document body **plus** an attacker-injected exfiltration payload. Blob-level taint contaminates the entire response — so a privileged LLM's clean summary is refused at egress (false positive), OR the system runs without taint and the payload leaks (false negative).

### What v1.2 ships

1. **Per-byte taint engine** (`backend/security/taint_engine_v2.py`) — a `TaintedBuffer` carries a parallel `colors[]` array (one label per content byte: PUBLIC / UNTRUSTED / SECRET / TOXIC). `slice`, `concat`, and `label_range` preserve per-byte fidelity. The clean document body keeps its low label; only the attacker's bytes carry TOXIC.

2. **Production integration at the chokepoint** (`backend/ai/agents/dual_llm_router.py`) — every agent tool result (web_search, fetch_url, read_file, …) flows through `DualLLMRouter.route_tool_result()` and now carries a `TaintedBuffer`. One integration point colors all tool outputs.

3. **Kernel-enforced write-gate** (`kernel/src/sec/taint_gate.c` + `backend/security/kernel_gate_connector.py`) — an eBPF LSM program attached to `bpf_lsm_file_permission` and `bpf_lsm_socket_sendmsg`. The userspace bridge pushes the per-(pid, fd) color array into a pinned BPF map; the kernel hook computes the max color over the write range and returns `-EPERM` when it exceeds the sink-policy ceiling.

4. **Per-byte mode** (the EchoLeak kernel defense) — using the verifier-friendly `bpf_loop()` helper (kernel ≥ 5.17), the gate walks `colors[write_start : write_start + min(len, 4096)]` and decides on the **actual bytes being written**. A write covering only the clean prefix is **ALLOWED** even though the same buffer contains TOXIC bytes elsewhere. This is the C-1 slice-then-egress idiom, now enforced in the kernel.

### Honest scope ceilings (read before you deploy)

- The eBPF program ships as reviewed source + a `clang -target bpf` build (`kernel/bpf/Makefile`). **Activation is an operator step:** `cd kernel/bpf && sudo make load` on a Linux ≥ 5.17 host with `libbpf` + `bpftool` + bpffs mounted. Until loaded, the Python bridge runs in **MOCK mode** and logs a WARNING — pushes are recorded but **not enforced**. This is by design, not a bug.
- Per-byte loop bound is **4096 bytes per LSM hook invocation** (the `bpf_loop` verifier-tractable bound). Larger writes get the conservative per-fd fallback for the overflow; chunked-per-byte mode is a Sprint 19 follow-up.
- The struct layout shared between Python and the kernel (`kernel/include/vos/taint_maps.h`) is validated byte-for-byte by cross-platform tests, so a layout drift can't silently degrade enforcement.

## [C-3] Cryptographic Declassification — Ed25519

**Catalog item:** C7 extension.

A byte range can be downgraded (e.g. TOXIC → UNTRUSTED so it can egress) **only** with a signed `DeclassEvidence` record. The engine verifies, before applying the downgrade:

1. An **Ed25519 signature** over the canonical evidence struct.
2. The evidence's **SHA-256 binds the exact bytes** being downgraded.
3. The review timestamp is within a **5-minute window**.
4. The `target_label` matches the requested downgrade.

The result: *"this data was reviewed and cleared for egress"* becomes a cryptographic claim an auditor can verify — not a log line a bug or misconfigured policy can forge. BBS+ selective-disclosure and Groth16 DV-SNARK extensions (prove "I reviewed bytes [10:50)" or "the bytes match policy X" without revealing them) are staged for Sprint 19+.

## [B] Cross-Organization Identity Federation — SPIFFE / AIMS

**Catalog items:** F1 + F4 + F5 (was "partial" at Sprint 16 → "full-stack cross-org" at v1.2).

### The problem

> *"Cross-tenant agent identity (sub-contractor flows): an agent moves between orgs (consulting workflow); no federation standard."*

At Sprint 16, vOS could route a JWT-SVID to a pre-imported partner verifier — but bundle import was manual and AIMS attestation envelopes were single-domain only.

### What v1.2 ships

1. **SPIFFE Trust Bundle synchronization** (`backend/services/identity_federation_bridge.py`, Cluster B.1) — registers partner trust domains, polls their bundle endpoints, validates each refresh (JSON shape, trust-domain cross-check, **sequence-number monotonicity** with REGRESSION-reject + an explicit `force_rollback` escape hatch, `pinned_sha256` tamper resistance), and **atomically** re-registers the verifier on key rotation so no concurrent verify sees a partial state.

2. **Cross-domain AIMS envelope verification** (`backend/services/aims_partner_verifier.py`, Cluster B.2) — a vOS instance in Trust Domain A verifies an agent's hardware-integrity AIMS envelope (carrying RTMR[0..3] attestation links) issued in Trust Domain B, end-to-end, using **only** the bridge-synced bundle keys (Ed25519 / RFC 8037 JWK). No shared signing infrastructure between the orgs.

The flow: an agent obtains a JWT-SVID, builds an AIMS envelope binding its hardware attestation, signs it; the receiving org looks up the partner's synced bundle, finds the JWK by `kid`, verifies the Ed25519 signature over the canonical envelope, runs the self-consistency checks, and returns a verified identity tagged with **which** trust domain it was verified in — so domain-scoped authorization policy can apply.

### Honest scope ceilings

- **Ed25519 only** for v1.2 (RSA + ECDSA are Sprint 19+).
- **No hardware-attestation policy registry yet** — B.2 verifies the partner's signature on the envelope but does not yet check the partner's RTMR measurements against a local hardware-policy table (Sprint 19+).
- **HTTPS_WEB profile only** (HTTPS_SPIFFE chicken-and-egg anchor is Wave B.4); **no background poller** (caller-driven `refresh_partner()` / `refresh_all()`); **in-memory bundle persistence** (restart drops registrations — Sprint 18.x wires durable storage).
- Standards alignment: IETF WIMSE working-group drafts (arch-07, workload-identity-bcp-02, workload-identity-practices-04, identifier-02) + the SPIFFE Federation specification.

## Upgrade / activation notes for operators

1. **Pull `main`** at or after `7db1db3`.
2. **Re-install backend deps with the lockfile:** `pip install -c backend/constraints.txt -r backend/requirements.txt`.
3. **(Linux ≥ 5.17 only, to enable kernel enforcement)** install `clang llvm libbpf-dev bpftool`, then `cd kernel/bpf && make && sudo make load`. Verify with `sudo bpftool map show pinned /sys/fs/bpf/vos3/taint_colors`. Without this step the byte-level gate runs in MOCK (advisory) mode.
4. **Federation:** register partner trust domains via `IdentityFederationBridge.register_partner(...)` and drive `refresh_partner()` on your own schedule (cron / FastAPI background task) until the async poller lands.
